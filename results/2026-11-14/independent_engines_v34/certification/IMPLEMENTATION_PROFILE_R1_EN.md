# V34 milestone JSON implementation profile R1

**Status: proposed profile, not an implementation or authorization to bypass the proof gate.** This binds the frozen `CERTIFICATE_SPEC_R1_EN.md` bytes, SHA-256 `5EAFCBAD47D93703ED3055959B4164CA3C1FDC5E4689A202FB9E790DDB2DCEF8`. The spec's mathematical requirements and edge cases apply. This profile specifies a wire envelope, validation and resource behavior, including the deterministic gate construction below. Full C028 compatibility and hypergraph fundamental independence remain OPEN.

## Strict JSON and input

Each request and response is one JSON value encoded as UTF-8, without BOM; only JSON whitespace may follow the value. Reject invalid UTF-8, invalid JSON, trailing non-whitespace, duplicate object member names after escape decoding at any nesting depth, non-finite numbers, unpaired Unicode surrogates and non-JSON values. JSON strings are sequences of Unicode scalar values; compare exactly after JSON escape decoding, with no Unicode normalization, case folding, character splitting, or locale collation. An integer means a JSON number with integer grammar `-?(0|[1-9][0-9]*)` and arbitrary-precision exact value; reject booleans, fractional/exponent notation, overflow and out-of-domain values. Limit checks apply before allocating arbitrary amounts of memory. Objects are unordered but every object must have exactly the keys specified; arrays are ordered. JSON is finite and no references, cycles, extensions or comments are permitted.

The original instance is supplied **separately**, as an independently trusted request field, and always validated and normalized by the consumer; do not accept a certificate's CNF, row coverage, instance hash or claimed normalized instance as a substitute. Its object has exactly `alphabet`, `positive`, `negative` as defined in the bound spec. This is a V34 milestone API, not C028's `Sigma`, `P`, `N` API; an adapter and C028 claims are outside scope.

A solver request is exactly `{ "instance": I, "kind": K, "limits": L }`, where K is `"logic"` or `"hypergraph"`; a verifier request is exactly `{ "instance": I, "certificate": C, "limits": L }`. L is exactly `{ "max_nodes": M }` where M is null (no explicit node cap) or an integer ≥0. An implementation may enforce additional documented limits on input bytes, nesting depth, wall time and memory; it must report INCOMPLETE when such a limit prevents a decision, rather than INVALID_INPUT or REJECT. `max_nodes` counts tree nodes *visited* in depth-first pre-order, including the root. A node can be entered only when the number already visited is less than M; therefore M=0 always yields INCOMPLETE for a valid request requiring a tree. For a solver this counts proof-tree construction nodes; for a verifier, proof-tree validation nodes. This is not C028 `max_candidates` and does not purport to preserve its semantics. Verification and preprocessing may independently exhaust limits. Cancellation, timeout or caught resource exhaustion return INCOMPLETE; hard termination may yield no response. No partial exact claim or certificate is returned on INCOMPLETE.

## Certificate format

C has exactly `{ "version": "v34-cert-r1", "kind": K, "claim": Q, "witness": W, "tree": T }`. Q is `"OPTIMAL"` or `"INFEASIBLE"`. W is null exactly for INFEASIBLE; for OPTIMAL it is an array of nonempty arrays of IDs. Validate blocks and coverage directly per spec; the empty witness is valid only for empty alphabet. Neither block order nor symbol order within a block makes a canonicality claim. The tree must be complete and have the following exact recursive forms:

- Logic conflict: `{ "tag": "conflict" }`.
- Logic split: `{ "tag": "split", "v": V, "zero": T0, "one": T1 }`. T0 and T1 are logic nodes checked under the corresponding value. The verifier rejects unknown or already-assigned names, omitted children and invalid conflict leaves.
- Hypergraph closed leaves: `{ "tag": "uncovered" }` or `{ "tag": "bound" }`; admissibility is exactly as in the bound spec, with bound forbidden for INFEASIBLE.
- Hypergraph branch: `{ "tag": "branch", "children": [ E0, ... ] }`; each E is exactly `{ "block": B, "child": T }`, B is an increasing array of distinct zero-based integer alphabet indices, and T is a hypergraph node. Require exactly all nonempty subsets of S containing its least index, sorted by the full length-m numeric 0-before-1 incidence vector specified in R1. Recompute R(B) and recurse with the specified S, U and q. Any duplicate, omission, wrong order, out-of-range index, extra field, or illegal leaf rejects.

`V` is a JSON array encoding one structural name, either `["Y",i,k]` or `["G",owner,path]`, with indices exact nonnegative integers. `owner` is `["A",k]` for active, `["E",n,p,k,i,j]` for equality, or `["C",n]` for negative coverage. `path` is an array of zero-based child indices from owner root, with `[]` naming that root; `G` prefixes and Y are disjoint. A name alone never supplies a gate or clause. Constants and identity results that are aliases of another variable are not fresh split variables. Tree names are matched against the verifier's own generated variables and branch assignments, not accepted on syntax alone.

### Deterministic CNF builder and names

The verifier builds the exact CNF from the normalized original instance, never from supplied clauses. Define `andlist` and `orlist` as a left-associated binary tree over the ordered operands; zero operands are respectively true and false, one operand is that operand unchanged. `not` is unary. **Never constant-fold a NOT, AND, or OR node**, even if one or all of its inputs are constants or identical. The only identities are the zero- and one-operand list rules just stated. Every actual NOT, binary AND and binary OR expression node has a fresh G variable; constants and references are leaves. Each owner's path starts at `[]`; left child is 0, right child 1, and unary child 0, recursively. A path denotes a gate only if that position is an actual operation node. If an owner root is a reference or a constant, the owner's output is that reference or constant and there is no root G variable. References to earlier owner outputs are leaves and are never inlined; they may alias or be constants. Thus a G path names exactly one node in its owner's expression tree before evaluating constants.

Construct owners and expressions in this order:

1. For each k from 0 to m-1, A(k) is `orlist([Y(0,k),...,Y(m-1,k)])`.
2. For each normalized negative index n, positive index p, slot k, prefix i from 0 through |n| and prefix j from 0 through |p|, in nested increasing order, E(n,p,k,i,j) has expression: E(0,0) is true; E(i,0) is `andlist([E(i-1,0),not(Y(index(n[i-1]),k))])`; E(0,j) is `andlist([E(0,j-1),not(Y(index(p[j-1]),k))])`; for i,j>0 it is `orlist([andlist([not(x),E(i-1,j)]),andlist([x,not(z),E(i,j-1)]),andlist([x,z,equal,E(i-1,j-1)])])`. Here x and z are the Y leaves for the indexed final symbols, equal is the literal Boolean result of exact ID equality, and each E reference is the output of the same (n,p,k) owner with the shown indices. All owner references are to previously constructed outputs.
3. For each negative n, C(n) is `orlist([andlist([A(k),andlist([not(E(n,p,k,|n|,|p|)) for p in increasing order])]) for k in increasing order])`. Repeated operations occurring in different places are separate nodes, not shared.

For each gate g with child inputs, enumerate valuations of the distinct underlying variable children, treating any literal constant as fixed and any alias as the same variable; append a clause excluding each valuation combined with an incorrect value for g. A clause excluding valuation b is the disjunction of each variable if b=0 and its negation if b=1. Add a unit clause asserting each C(n) output; true adds nothing and false adds an empty clause. Add the assignment and symmetry clauses and threshold clauses exactly as R1 specifies; if a threshold operand is constant, simplify that clause by its Boolean value, deleting true clauses and false literals. Deduplicate identical literals and drop tautologies. This defines the actual clause set regardless of clause enumeration order. For empty residual CNFs, conflict scanning costs O(L+1), not merely O(L); straightforward verification costs O(tree_nodes × (L+1)), plus construction and witness checking.

### Hypergraph leaf precedence

At every hypergraph node first accept a `bound` leaf exactly if the claim is OPTIMAL and `q+|S|≤k`; this includes a feasible leaf with S=U=empty and q≤k. Otherwise a `bound` leaf rejects. If the tag is `uncovered`, require S empty and U nonempty. If S is empty and neither admissible leaf applies, reject; in particular S=U=empty cannot be closed by `uncovered`. Otherwise require a complete branch. This explicitly resolves the conflicting leaf-order sentence in R1 without altering the original file; INFEASIBLE never accepts `bound`.
## Responses and checking

A solver response is exactly `{ "status": S, "certificate": C_or_null }`, with S one of `INVALID_INPUT`, `INCOMPLETE`, `OPTIMAL`, `INFEASIBLE`. For OPTIMAL or INFEASIBLE, C is a complete certificate with matching `claim` and requested `kind`; for INVALID_INPUT or INCOMPLETE it is null. No C, O, uniqueness, canonical-first witness, runtime comparison or C028-budget claim appears in this response. The solver must independently generate a proof and check success before returning an exact status; the consumer must still verify it independently.

A verifier response is exactly `{ "status": S }` where S is `ACCEPT`, `REJECT`, or `INCOMPLETE`. ACCEPT means the entire original instance, witness and tree were checked against the R1 claim, with complete document consumption. REJECT means a completed validation detected invalid instance, certificate syntax or mathematical proof; it is not a claim of mathematical infeasibility. INCOMPLETE means checking could not reach such a conclusion because of cancellation, a resource limit or caught interruption. Validly parsed but mathematically invalid trees must not be accepted. If a malformed suffix is encountered before any resource limit prevents parsing, return REJECT; if a limit prevents determining validity, return INCOMPLETE. On invalid request envelope or invalid solver instance, the solver returns INVALID_INPUT; implementation failures must not be disguised as mathematical outcomes.

No implementation, test, benchmark, external proof format or empirical performance claim is made. Independent review of this profile, the addendum and the eventual implementation is required.
