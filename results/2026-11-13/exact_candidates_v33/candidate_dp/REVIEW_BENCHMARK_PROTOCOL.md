# Independent benchmark-protocol and harness review

**Verdict: suitable for the stated bounded comparison, with the limitations below; no observed full-output mismatch or material fairness defect in the completed records inspected.** This is an independent reading of the protocol, frozen corpus and scripts, plus a read-only consistency inspection of the raw timing records. No benchmark was executed for this review; results are not a proof of general speed or correctness.

Reviewed `audit/PROTOCOL.md` SHA-256 `CB1E4BA7EA259B1F6E74D244AAFE1E9EE9EE5DDF5FEB5654A88F86CBCDDC40BE`, `audit/run_timing.py` SHA-256 `9EF280C6C608DDDCA3E711DFD70532F8FD968FC987EC646B196FF0E653C158E0`, `audit/summarize_timing.py` SHA-256 `4F6EB820ABB805EE6E1709E6F05003F763BE1DCBDEDAEF2B653165D4DD3686DA`, and `audit/timing_cases.jsonl` SHA-256 `013E2B60DC1D5740D766A9B0F77C458C4FBB92F203EE67977F3FE7104B48215B`; the corpus hash matches the predeclared protocol and harness constant. Candidate dependency provenance still requires the separately recorded review and hashes.

1. **Equivalent task:** all four designated entry points receive each same record with unlimited `max_candidates` and return the full C028 result. The timed call encloses candidate preprocessing, DP or graph search, witness reconstruction and replay, and result creation. It does not omit costs to compare an optimum-only algorithm. Budget semantics were separately checked, not timed.
2. **Timing boundary and units:** each trial runs in a fresh child, imports the module and dependencies first, starts `perf_counter_ns` immediately before `solve`, then stops immediately after. Import and output JSON serialization are excluded from `solve_ns`; parent `startup_wall_ns` includes child process startup, loading, solve and serialization/capture. Summary divides nanoseconds by 1e9, yielding seconds. Startup-inclusive numbers cannot be substituted for warm call costs and include serialization/scheduling.
3. **Order and caps:** a fixed cyclic order rotates the four solvers by case and repeat; there are three trials per solver/case. `subprocess.run(timeout=20)` bounds the whole child process, not only solve; a timeout is a censored outer-wall observation, with no numeric solve time or valid speed ratio. Source digests are checked before the matrix and again in each child before import. The auditor's recorded correctness gate precedes timing. Three trials and synthetic inputs limit conclusions; host load, caching and thermal effects remain possible.
4. **Full outputs:** read-only inspection of the completed raw snapshot found ten case IDs, twelve records per case, three per solver; all 120 processes report OK and all result statuses are complete (AMBIGUOUS or UNIQUE_COMPATIBLE). For each case all twelve complete result objects compare equal after key-order normalization. The code retains full JSON results and stdout/stderr for verification. This is a consistency check, not an independent mathematical oracle for the timing dataset.
5. **Summary limitations:** `summarize_timing.py` computes a median only for a solver with three successful complete results and agreement among the complete results of that case. In a hypothetical future run containing `INCOMPLETE` or `ERROR` result objects returned by a process with exit code 0, those objects are excluded from its agreement set, and the displayed status may remain process-level `OK`; therefore report actual result status separately and never treat such a record as a completed comparable solve. This limitation did not affect the inspected snapshot, where every result is complete. The summary does not itself prove that each repeat index is unique or validate exact input identifiers; the raw inspection above verifies the count per solver but final reporting should retain the full raw data and corpus.
6. **Capture/dependency limits:** despite the protocol's phrase “bounded stdout/stderr,” `capture_output=True` has no explicit byte cap; the time cap is not an output-size cap. No observed problem follows for these completed records. The harness hashes each top-level source, but the graph candidate imports `baseline_contract.py` without runtime hash enforcement; the separately reviewed graph manifest binds it to the C028 hash. A release audit should retain/check that dependency hash and not imply the harness alone enforced it throughout the run. DP verifies its reference hash on import. No memory metric is recorded, and none should be inferred.

The official audit must still bind and publish the final raw, summary, environment, source/dependency hashes and correctness verdict, explicitly indicate whether runs were contemporaneously affected by other workload, and refrain from generalizing synthetic outcomes. Largest overlooked issue: a child-process OK or an optimum-only value is not equivalent to a completed full-contract result; all repeated serialized outputs and actual solver statuses must be checked before comparing times.
